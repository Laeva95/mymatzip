### 37. 맛집 마다 리뷰 평점을 쿼리로 DB에서 가져와서 쿼리가 N+1 번 발생함

- **발견 근거:** 테스트 파일을 통한 쿼리 및 지연 시간 확인
- **Before:** 쿼리 7회 / 지연 시간 5.11ms
- **원인:** 반복문을 통해 쿼리를 반복해서 날림
- **개선:** dto 클래스를 통해 모든 리뷰 평점을 한번에 가져와서 저장
- **After:** 쿼리 2회 / 지연 시간 4.44ms
- **재발 방지:** 반복문을 통해 DB에 접근하지 않도록 방지

### 47. RDS My SQL 커넥션 풀 초과로 인한 접속 불가 문제 발생

- **발견 근거:** 데이터베이스 접속 불가로 인한 프로젝트 실행 오류
- **Before:** 일부 팀원 프로젝트 실행 오류
- **원인:** RDS 커넥션 풀 제한이 60개인데, 각 연결 마다 10개의 커넥션 풀을 사용해서 최대치를 초과하여 접속 불가
- **개선:** application.properties 파일에서 spring.datasource.hikari.maximum-pool-size=5 설정을 통해 각 연결의 커넥션 풀을 5개로 적용
- **After:** 팀원 전원 프로젝트 실행 성공
- **재발 방지:** 설정을 통해 커넥션 풀 사용 최대치 제한

### 51. test_application 컬럼 추가로 인한 서버 시작 에러

- **발견 근거:** 실행 로그에서 'alter table owner_application add column test_application boolean not null default false not null' / not null이 두번 표시됨
- **Before:** @Column(nullable = false, columnDefinition = "boolean not null default false")
- **원인:** columnDefinition에 not null을 직접 적었는데, nullable = false를 보고 Hibernate가 not null을 한 번 더 붙임
- **개선:** columnDefinition에는 타입과 기본값만 적고, NULL 허용 여부는 JPA 속성(nullable)에서만 정함
- **After:** @Column(nullable = false, columnDefinition = "boolean default false") → boolean default false not null이 정상적으로 만들어짐
- **재발 방지:** (적용) 엔티티 주석에 "제약 조건은 JPA 속성으로만"을 적어 둠

### 53. 2020-02-30이나 미래 날짜가 국세청 API까지 전송됨. 결과가 "국세청 등록 정보와 일치하지 않습니다"로만 나와서 날짜가 틀린 줄 알 수 없음

- **발견 근거:** 코드 점검. 서버는 @Pattern("^\d{4}-\d{2}-\d{2}$")으로 형식만 검사하고, 미래 날짜는 화면의 max 속성으로만 막음
- **Before:** 잘못된 날짜 → 국세청 호출 → "일치하지 않습니다"
- **원인:** 형식만 확인하고 실제로 있는 날짜인지는 검사하지 않음. 화면을 거치지 않은 요청(Postman 등)은 그대로 통과
- **개선:** 국세청을 부르기 전에 checkOpenDate()를 실행함. LocalDate.parse()는 없는 날짜를 거부하고, 미래인지는 Asia/Seoul 날짜 기준으로 비교함
- **After:** "개업일자가 올바른 날짜가 아닙니다" 또는 "오늘 이후 날짜일 수 없습니다" (400). 국세청은 호출하지 않음
- **재발 방지:** 검사 순서를 "입력 검증 → 외부 API 호출"로 고정함 (체크섬, 주소, 날짜를 모두 국세청 호출 전에 검사)

### 57. 다른 회원 두 명이 같은 사업자번호로 몇 초 차이로 실제 신청하면 두 신청이 모두 심사 중으로 접수됨. 관리자가 둘 다 승인하면 한 사업자번호에 OWNER 계정이 두 개 생김

- **발견 근거:** 국세청 확인(몇 초)이 트랜잭션 밖에서 실행돼서, 그 사이 상대 신청이 아직 저장되지 않았으면 두 신청 모두 중복 검사를 통과함
- **Before:** 같은 번호로 심사 중인 신청 A, B가 있을 때 A를 승인한 뒤 B도 승인할 수 있음 → OWNER 두 명
- **원인:** 중복 검사가 신청 시점에 한 번뿐이고, 사업자번호 단위로 잠그지 않음. 반려된 신청은 같은 번호를 다시 써야 해서 DB UNIQUE 제약도 걸 수 없음
- **개선:** 관리자 승인 단계에서 다시 검사함. approve()에서 실제 신청이면 isApprovedByOtherMember()로 같은 번호의 다른 회원 승인 신청이 있는지 확인하고, 있으면 IllegalStateException(409)을 던짐. 예외가 나면 트랜잭션 전체가 되돌아가서 상태와 역할이 바뀌지 않음. 하이픈이 붙은 예전 데이터도 같은 번호로 알아보도록 두 모양으로 확인함
- **After:** B를 승인하면 409 → B는 심사 중으로 남고(반려 가능), 회원 역할도 바뀌지 않음
- **재발 방지:** 신청 시 검사와 승인 시 검사를 같은 규칙으로 맞춤: 실제 신청만 검사, 테스트 신청과 본인 신청은 제외

### 58. 맛집 목록 조회 시 맛집마다 평균 별점 쿼리가 1번씩 추가 실행됨 (N+1)

- **발견 근거:** SQL 로그에서 같은 평균 별점 쿼리(WHERE restaurant_id = ?)가 맛집 수만큼 반복 출력됨
- **Before:** 목록 화면 12개 → 쿼리 14번 / 전체 목록 API 100개 → 101번 (1+N)
- **원인:** 목록을 DTO로 바꿀 때 맛집 1개용 toResponse()를 반복 호출해서, 호출마다 평균 쿼리가 실행됨
- **개선:** 맛집 id를 모아 IN + GROUP BY 쿼리 1번으로 평균 별점을 일괄 조회해 Map으로 매핑 (AvoidNPlusOne 메서드 7개 추가, 기존 메서드 유지)
- **After:** 목록 화면 14→3번 / 전체 API 101→2번. 맛집 수와 상관없이 2~3번으로 고정
- **재발 방지:** 목록 응답은 일괄 조회 메서드를 사용하고, 쿼리 수 비교 테스트를 유지 (변경 후 쿼리 ≤ 3이어야 통과)

### 59. 표기만 다른 같은 가게를 다른 가게로 판단해 중복 저장됨

- **발견 근거:** 미리보기 결과 파일(CSV)에서 이름과 도로명·건물번호가 같은데 주소 띄어쓰기·괄호·층·호·건물명만 다른 행이 각각 "성공"으로 저장 예정이었음

### 20. 없는 맛집 찜, 찜하지 않은 맛집 취소, 이미 찜한 맛집 등록 시 부적절한 HTTP 상태 코드가 반환되는 문제

### 1. 없는 ID를 삭제해도 403 반환

- **발견 근거:** 삭제 요청에서 '없는 리뷰·답글'과 '권한 없음'을 구분하지 않고 모두 403으로 응답한다.

- **원인:** 모든 IllegalArgumentException을 403으로 일괄 처리
- **개선:** 없음은 404, 권한 없음은 403으로 예외 종류를 나눔
- **After:** 404
- **재발 방지:** 예외 종류별 상태코드 매핑 테스트 추가 (없음 404, 권한 없음 403)

- **개선:** 신고 기록 테이블(회원·리뷰 유일키)로 중복 방지, 본인 리뷰 신고 차단
